# 공개 유스케이스와 mock 규약

이 규약은 현재 marketplace와 앞으로 추가할 모든 킷에 적용한다. 킷은 SDK이며 실행 시점·저장·수집 순서·진행 상태·앱 재시도 정책은 앱이 소유한다. 내부 의존 방향은 [SDK 헥사고날 설계](architecture.md)를 따른다.

## 앱이 사용하는 계약

앱은 킷의 공개 유스케이스 입력 포트를 사용한다. 업무 이름을 드러내는 `<Action>UseCase`와 명시적인 `execute(input)` 계약을 제공한다. 생성 함수는 실제 구현 또는 mock 구현을 조립해 같은 입력 포트 타입을 반환한다. 앱의 조립 지점에서 구현을 선택하고 기능을 호출하는 코드는 공통으로 유지한다. 필요한 HTTP·MCP 변환이 생기면 인바운드 어댑터를 추가할 수 있다.

```text
앱 → 공개 유스케이스 입력 포트
       ├─ 실제 구현 → 아웃바운드 포트 → 외부 어댑터
       └─ mock 구현 → 앱이 주입한 공개 반환 모델
```

mock은 공개 유스케이스 입력 포트의 대체 구현이다. 실제 유스케이스나 마켓 어댑터를 호출하지 않는다. 앱이 결과로 받는 타입 전체를 mock 결과로 주입한다. 내부 포트의 반환 타입, 외부 제공자의 원문 DTO, mock 전용 업무 모델로 변환하는 일을 앱에 요구하지 않는다. 관측 시각·식별자·정밀 금액·커서·조회 범위도 주입한 값을 유지한다.

## 제공 방식과 실행 의미

각 킷은 `/testing` 공개 진입점에서 업무별 mock 생성 함수와 설정 타입을 제공한다. 실제 기능·mock의 생성 방법과 같은 앱 함수에 교체 주입하는 실행 예제를 README에 연결한다. 내부 소스나 아웃바운드 포트를 앱에 공개해서 mock을 만들게 하지 않는다. 공통 문자열 명령·동적 등록 엔진으로 서로 다른 킷의 업무 타입을 합치지 않는다.

- 요청별 성공 결과 또는 정규화된 오류 시나리오를 명시한다. 요청 매칭에 쓰는 필드와 취소 신호처럼 매칭에서 제외하는 필드를 문서화한다.
- 같은 요청은 반복·병렬 호출에서 같은 결과를 반환한다. 호출 순서에 의존하는 응답 큐·전역 상태는 기본 계약에 포함하지 않는다.
- 미등록 요청과 중복 시나리오는 명시적인 구성 오류다. 빈 결과는 빈 결과를 설정한 시나리오에서만 반환한다.
- 생성 시 입력 데이터를 복사하고 호출마다 독립된 결과/오류를 만든다. 앱이 fixture나 반환값을 변경해도 다른 호출·인스턴스에 영향을 주지 않는다.
- mock은 자격증명·외부 통신·환경변수·DB·타이머 없이 동작한다. 사전 취소된 호출은 공개 취소 오류로 반환한다.
- 오류는 실제 구현과 같은 오류 분류·공개 메타데이터 계약을 사용한다. 원본 exception·제공자 응답·비밀값을 전달하지 않는다.

`/testing`의 실행 import 경로는 서버 인증 구현을 로드하지 않는다. 지원 런타임은 실제 패키지 소비 검증 범위로 표시하며 브라우저·앱 배포 호환성을 추정해 표시하지 않는다. fixture에는 합성 또는 적절히 비식별화된 공개 반환 데이터만 사용한다.

## Fixture 빌더와 공통 모델 검증

모든 킷은 공개 반환 모델을 쉽게 만드는 업무별 함수형 빌더를 `/testing`에서 제공한다. 앱은 필요한 값만 지정하고 합성 기본값으로 필수 필드를 채운다. 빌더의 결과는 실제 공개 모델이며 별도 wrapper나 변환이 필요하지 않다. 기본 시각은 명시한 입력으로 결정하고 ID는 빌더 인스턴스 안에서 생성한다. 같은 설정·호출 순서는 같은 결과를 만들며 전역 카운터·현재 시각·난수에 의존하지 않는다. 생성 ID는 인스턴스에 먼저 제공된 ID와 충돌하지 않게 예약하고, 명시적으로 중복한 ID는 해당 모델을 구성할 때 검증한다.

입력과 결과를 복사하고, 명시한 값을 조용히 고치지 않는다. 제공자 원문 상태나 금액을 추측 변환하지 않으며 업무상 자동 계산이 필요한 경우 그 기능의 계약으로 별도 정의한다. 예를 들어 주문 금액은 할인·환불 때문에 단가×수량과 다를 수 있으므로 빌더가 정산하지 않는다.

공개 모델의 검증은 domain의 공통 검증기가 소유한다. 실제 유스케이스 결과와 fixture 빌더·직접 mock 주입이 같은 검증기를 재사용한다. 중첩 필드·정밀 값·식별자 중복·데이터 관계·연결/조회 범위 일관성을 해당 업무 계약에 맞게 확인한다. 빌더 사용 여부와 TypeScript 컴파일 여부에 따라 검증이 달라지지 않게 한다. 이 검증은 외부 전문 해석이나 제공자별 조회 제한을 대체하지 않는다.

mock과 빌더의 구성 오류는 해당 킷의 정규화 오류와 `path`를 제공한다. 경로는 시나리오/항목/필드 위치를 식별하고 오류 메시지는 기대 조건을 설명한다. 잘못된 값·원문 exception·개인정보를 메시지에 넣지 않는다. 실제 유스케이스가 잘못된 결과를 얻으면 안전한 응답 계약 오류로 변환한다. 유효한 fixture의 관측 시각·금액·식별자·커서는 검증으로 변경하지 않는다.

## 테스트의 구분과 완료 기준

| 테스트 대상 | 대체 지점 | 주입 데이터 |
| --- | --- | --- |
| 앱의 화면·저장·페이지 순회·오류 처리 | 공개 유스케이스 입력 포트 | 실제 반환 타입 |
| 킷의 유스케이스 업무 규칙 | 내부 아웃바운드 포트 | 포트의 내부 계약 |
| 실제 외부 어댑터의 인증·요청·응답 변환 | HTTP 등 외부 통신 | 제공자 원문 fixture |

앱용 mock 성공을 실제 어댑터·외부 계정 검증으로 취급하지 않는다. mock은 설정한 시나리오의 결과를 재현하며 제공자 API 전체의 제약을 에뮬레이션하지 않는다.

킷의 공개 기능을 추가·변경할 때 실제/mock의 동일한 입력·출력 타입, 앱의 공통 소비 함수, 결과 전체 재현, 빈 결과·오류·커서·요청 누락·사전 취소·반복/병렬 호출·데이터 격리를 해당 기능에 맞게 검증한다. 실제 배포 산출물의 `/testing` import·타입·실행도 검사한다. 공개 계약을 변경하면 mock·앱 소비 예제·전환 문서를 함께 갱신하고 미사용 계약을 제거한다.

빌더의 결정적인 기본값·명시 override·ID 예약·복사 격리, 직접 주입 데이터의 오류 경로와 실제 결과의 안전한 실패도 검증한다. 실제 패키지 소비 예제에서 빌더→mock→앱의 공통 소비 함수를 실행하고 공개 모델 타입에 그대로 대입할 수 있어야 한다.
